# init scaffolds a config that references prompt files it never creates

## Requirement

`local-board init` scaffolds a config whose `optionalSteps` entries point at `plans/prompts/optional-steps/...` (`src/config.js:776-807`) and `gate-check` hardcodes `plans/prompts/steps/gate-check.md` (`src/cli.js:779`), but `src/scaffold.js` FILES creates neither `gate-check.md` nor any `optional-steps/*` prompt. Those files exist only in this repo's live `plans/` tree. In a freshly initialized repo, `gate-check --json` and `specialty-run` return `prompt` paths that do not exist, handing dispatched agents dead file references.

Fix: add the missing prompt files to the scaffold, and make `gate-check`/`specialty-run` verify the resolved prompt file exists and fail loudly when it does not.

Acceptance: after `init` in an empty repo, every prompt path returned by `gate-check` and `specialty-run` exists on disk; missing prompts produce a clear error, not a dead path.

## Technical Design

## Problem restated

`local-board init` scaffolds `plans/local-board.config.jsonc` whose `optionalSteps`
entries reference `plans/prompts/optional-steps/...` and whose `gate-check` action
resolves `plans/prompts/steps/gate-check.md` (`src/cli.js:821`), but
`src/scaffold.js` `FILES` creates neither the `optional-steps/*` prompts nor
`gate-check.md`. A freshly initialized board therefore returns `prompt` paths that
do not exist, handing dispatched agents dead file references. Two independent
defects: (1) the scaffold is incomplete, and (2) `gate-check`/`specialty-run`
resolve prompt paths without verifying they exist.

## Relevant current state

- `src/scaffold.js` `FILES` inlines a *thin, hand-written* subset of prompts
  (`roles/*`, `steps/decompose|design|test|document`). These inline bodies are a
  third, drifting copy: they are shorter than and differ from the real prompts in
  `plans/prompts/` and their mirror in `resources/prompts/`. Nothing keeps them in
  sync (the drift-guard test in `test/resources-sync.test.js` only pins
  `resources/` ↔ this repo's `plans/`).
- `resources/prompts/` (landed T20260707T1318Z) is the packaged mirror of this
  repo's `plans/prompts/` and ships via the `files` allowlist (`package.json:24`,
  asserted by `test/pack.test.js`). It contains the full set: `steps/gate-check.md`,
  `steps/estimate.md`, `roles/estimator.md`, and all five `optional-steps/*`
  prompts the default config references, regenerated by `scripts/sync-resources.mjs`.
- `resources/templates/ticket.md` similarly mirrors `plans/templates/ticket.md`
  (another inline `FILES` duplicate).
- `src/cli.js` `commandGateCheck` builds `promptPath` as
  `path.resolve(root, "plans", "prompts", "steps", "gate-check.md")` and returns it
  unconditionally. `commandSpecialtyRun` builds `path.resolve(root, entry.prompt)`
  and returns it unconditionally. Neither calls `access`/`existsSync`.
- **Runtime-layout wrinkle (must handle):** `src/install.js:164-165` copies
  `resources/prompts` → `<installDir>/prompts` and `resources/templates` →
  `<installDir>/templates` — it *flattens* `resources/` away. So the packaged prompt
  tree lives at `<pkgRoot>/resources/prompts` in a dev clone / global npm install,
  but at `<pkgRoot>/prompts` when running from `~/.local-board`. Any init-time read
  of packaged prompts must probe both layouts.
- `SKILL.md:89` already documents a skill-level fallback: "If a returned prompt is
  missing, use fallback prompts from `<<INSTALL_PATH>>/prompts/`." That guidance is
  Claude-skill-only, advisory, and not enforced in CLI output — it does not fix the
  dead JSON `prompt` path for other harnesses.

## Approach

Two coordinated changes.

### 1. Scaffold the real prompt tree from packaged `resources/`

Stop inlining prompt bodies. At `init`, recursively copy the packaged
`resources/prompts` tree into the new project's `plans/prompts/`, and (for the same
single-source reason) `resources/templates` into `plans/templates/`. This gives
fresh boards exactly the maintained, dogfooded prompts — including `gate-check.md`
and every `optional-steps/*` the default config references — and deletes the
drifting inline third copy.

Decision — **copy the whole `resources/prompts` tree**, not just the
config-referenced subset. It is strictly more useful (ships `estimator.md`,
`estimate.md`, etc.), needs no enumeration to stay correct as the catalog grows,
and keeps a scaffolded board identical to the packaged runtime set. Enumerating
"only referenced" prompts would re-introduce a maintenance coupling every time an
optional step is added.

Implementation notes:
- Add a `packagedResourceDir(name)` resolver in `src/scaffold.js` using the
  `dirname(fileURLToPath(import.meta.url))` → package-root pattern already used in
  `src/install.js:20` and the hooks. Probe, in order:
  `<pkgRoot>/resources/<name>` (dev clone / global npm) then `<pkgRoot>/<name>`
  (the `~/.local-board` flattened layout). Throw a clear error if neither exists so
  a packaging regression fails loudly rather than silently scaffolding an empty
  tree.
- Replace the inline prompt/template entries in `FILES` with a directory walk:
  `readdir` the resolved `prompts` and `templates` dirs recursively and route every
  file through the existing `writeScaffoldFile`, preserving its `wx`-vs-`w`
  idempotency, `--overwrite` semantics, and `created`/`skipped` accounting. Do **not**
  use a bare `cpSync` — it would bypass the skip-if-exists contract that the
  idempotency tests depend on.
- Keep the two `README.md` entries (`plans/README.md`, `plans/tickets/README.md`)
  inline; they have no `resources/` counterpart. Drop the now-redundant explicit
  `mkdir` of `prompts/roles` and `prompts/steps` (the walk creates dirs as needed),
  or leave them — harmless.

### 2. Verify the resolved prompt exists; fail loudly

Add a shared helper (e.g. `resolveExistingPrompt(root, relPath, { action })` in
`src/cli.js` or a small `src/prompts.js`) that resolves the project-local path and
`access()`-checks it. On success return the absolute path unchanged. On ENOENT
throw an actionable `Error` naming the missing path and the remedy — e.g.
`gate-check: prompt not found at <path>. Run "local-board init" in this repo to
scaffold missing prompts, or restore plans/prompts/steps/gate-check.md.` This is
the intended behavior for **back-compat with boards initialized before this fix**:
they get a clear, actionable error instead of a dead path or a downstream
stack-trace when an agent tries to open the missing file.

- `commandGateCheck`: verify the `gate-check.md` path before emitting the payload.
- `commandSpecialtyRun`: verify `path.resolve(root, entry.prompt)` before emitting
  the payload.
- Decision — **loud error, not silent packaged-fallback.** The acceptance criteria
  explicitly want "a clear error, not a dead path," and an error keeps the failure
  visible to the human running an old board. (A silent fallback to
  `<installDir>/prompts/...` was considered — it matches `SKILL.md:89`'s intent —
  but it hides board drift and re-introduces the layout-probe complexity into the
  hot path. Keep the skill-level fallback text as the soft cushion; make the CLI
  authoritative and strict.)

## Risks and edge cases

- **Packaged-path resolution across layouts** (dev clone, global npm, flattened
  `~/.local-board`). If the resolver misses, init scaffolds an incomplete tree.
  Mitigation: probe both `resources/<name>` and `<name>`; throw if neither resolves.
- **Idempotency / `--overwrite`:** the directory walk must reuse `writeScaffoldFile`
  so existing files are skipped (`wx`) unless `--overwrite`, matching current tests.
- **Existing tests asserting inline prompt content** will break by design; update
  them to assert against the copied `resources/` content (or just assert file
  existence + non-empty), not fixed strings.
- **New optional step added to default config without a matching resource** would
  now be caught: the "every config-referenced prompt exists after init" guard test
  fails, which is the desired safety net.
- **Empty-catalog gate-check** must not error on a missing prompt (see T1333
  coordination).
- **Scaffold content growth:** real prompts are richer than the old inline stubs —
  intended and beneficial; no behavioral risk.

## Test strategy

  every `DEFAULT_CONFIG.optionalSteps[*].prompt` path exist and are non-empty; assert
  the full `resources/prompts` file set is mirrored into `plans/prompts` (reuse the
  walk-and-compare style from `test/resources-sync.test.js`).
- Guard test encoding the acceptance criterion: after init, iterate the default
  config's `optionalSteps` prompts + the gate-check path and assert each exists on
  disk — regression net for future catalog additions.
- Idempotency: second `initProject` reports all prompts skipped; `--overwrite`
  refreshes them.
- `gate-check`/`specialty-run` (via `src/cli.js` or the CLI): after init, JSON
  `prompt` path exists. Then delete the prompt and assert the command throws an
  actionable error and exits non-zero (no raw stack trace / ENOENT leak).
- Existing `initProject` tests in `test/tickets.test.js` continue to pass after
  updating inline-content assertions.
